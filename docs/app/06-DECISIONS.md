# Decisions

### D-001 — No Base44↔GitHub sync; app source lives in a separate repo
**Status:** Active
**Decision:** This repo (`cathys-kitchen`) does not connect Base44's GitHub sync. It holds only the durable spec/decision record (`docs/app/*.md`) and PR history. The actual Base44 app source for Cathy's Kitchen lives in `TFRS-Admin/cathy-kitchen-2` — a pre-existing Base44 app scaffold (originally built and branded for a different, unrelated business) that is being rebranded and repointed for this project rather than built from scratch.
**Why:** `docs/REPO_SETTINGS.md` protects `main` here (PR-only, linear history); a second writer syncing from Base44 would conflict with that. A working Base44 React/Vite scaffold with reusable entity/RLS/admin-auth patterns already existed, so adapting it was smaller than building a second app via the builder AI from zero.
**Implication:** Future agents implementing or changing the actual site should work in `TFRS-Admin/cathy-kitchen-2`, not here. Changes to business facts, data model, or integration design still get recorded in this repo's `docs/app/*.md` first.

### D-002 — System boundary: Base44 is the entire public site and native form surface; GHL is the sole system of record
**Status:** Superseded by D-009 — GHL is no longer part of this project at all; kept for history
**Decision:** Native Base44 forms call narrow Base44 server-side functions that write to GoHighLevel via its API using server-side secrets — not redirects to GHL-hosted forms. No customer, order, or catering data may be intentionally stored in any Base44 data table; Base44 entities hold public website content only (menu, FAQs, photos, site settings). At the time this was written the site had three planned native forms (weekly dinner request, catering inquiry, email signup); only catering inquiry exists today — see D-008.
**Why:** Explicit, current owner instruction, overriding the original brief's "safest first integration" recommendation (GHL-hosted-form redirects) per the authority order in `00-README.md` (owner's current instruction ranks above the approved build brief).
**Implication:** Any future form or data model change must keep customer data out of Base44. The GHL credential and location/pipeline/field/tag IDs must be verified against the real Cathy's Kitchen GHL account before use — never assumed from another client's account in the workspace.

### D-003 — `MenuDay.serve_date` is stored explicitly
**Status:** Active
**Decision:** Each `MenuDay` record stores its own `serve_date`, rather than deriving it from `MenuWeek.week_start_date + day_of_week` at render time.
**Why:** Avoids timezone and week-rollover bugs around "what is today/this week" for a cutoff- and pickup-window-driven site.
**Implication:** Any menu-creation flow (e.g. "Create Next Week") must compute and persist `serve_date` for each day up front.

### D-004 — No per-dish GHL form or link
**Status:** Superseded by D-008 (the weekly-order form it refers to was removed) and D-009 (GHL dropped entirely); kept for history
**Decision:** The per-dish "Request this dinner" control opens the single native weekly-order form with that dish preselected, rather than a separate form or a separate GHL destination per dish.
**Why:** Keeps one request form and one GHL integration path; avoids multiplying forms/functions per dish.
**Implication:** Do not add a second native or GHL-hosted form for individual dishes.

### D-005 — The approved build brief is the design authority
**Status:** Active

**Why:** `00-README.md`'s authority order ranks the approved build brief above `03-DESIGN.md` itself; this makes "verify design fidelity" (per `AGENTS.md`'s required workflow) executable instead of undefined.

### D-006 — GHL asset creation is scoped and verified before any Base44 secret is set
**Status:** Superseded by D-009 — moot, no GHL asset or secret is being created; kept for history
**Decision:** The GHL location, pipelines, stages, most custom fields, and tags are confirmed/created against the real, verified Cathy's Kitchen GHL account before any corresponding Base44 secret is configured. Nothing is assumed from another client's location in the connected workspace.
**Why:** None of the GHL locations visible in the connected workspace matches Cathy's Kitchen; using the wrong location/credential would be a serious data-routing error.
**Implication:** Treat "no verified GHL location/credential yet" as a stop condition for wiring the real integration (see `04-ARCHITECTURE.md`), not something to work around with a guess.

### D-007 — The interim owner-notification-email fallback is pre-launch scaffolding only; it is a launch-blocking gap, not an accepted second integration path
**Status:** Superseded by D-009 — the owner-notification email is now the permanent mechanism for catering, not an interim gap; kept for history
**Decision:** Until real GHL secrets are set, the catering form in `TFRS-Admin/cathy-kitchen-2` (`sendOrder`) falls back to emailing the owner instead of writing to GHL. This exists solely so the form can be built and tested end-to-end before GHL is wired up. The site must not be published (`SiteSettings.content_status` set to `live`, or a public domain attached) while this fallback is still active.
**Why:** Caught by automated review on PR #1 — as originally documented, this fallback contradicted BR-001 ("GHL is the sole system of record") and acceptance test #11 ("no form submission sends an email... until GHL activation is separately approved"). Nothing in the code or docs previously stopped this interim mechanism from reaching real customer traffic if the app were prematurely linked/published; it is real customer PII (name, phone) transiting through an ad hoc, unapproved channel outside GHL.
**Implication:** The real GHL catering write path (`TFRS-Admin/cathy-kitchen-2`#20) is a hard prerequisite for publish, not a nice-to-have — see `04-ARCHITECTURE.md`'s constraints. It's implemented but inert until the GHL secrets listed there are set; any future agent finding the fallback still active at publish time must treat it as a stop condition, not proceed. Weekly ordering has no equivalent gate — see D-008.

### D-008 — Weekly ordering has no native Base44 form; it is a direct SMS to a GHL-owned number. Catering keeps D-002's original shape.
**Status:** Partially superseded by D-009 — weekly ordering still has no native form and is still a plain SMS link (that part holds), but the planned swap to a GHL-owned number, and catering's GHL integration, are both dropped
**Decision:** D-002 described a native "weekly dinner request" form calling a Base44 function that writes to GHL. That form was removed from `TFRS-Admin/cathy-kitchen-2` when the torn-paper design system was adopted (the system doesn't support a multi-field order form; the owner confirmed removing it rather than inventing a component outside the system) — weekly ordering is now a plain "Text to order" `sms:` link to a number `SiteSettings` stores. Per explicit owner instruction, that number is being replaced with one GHL provisions and owns, so inbound order texts land in GHL's own Conversations/CRM and auto-create a contact with zero Base44 code — Cathy will check order texts in GHL going forward, not her personal Messages app. The catering inquiry form is the one native form that still exists, and keeps D-002's original integration shape (Base44 function → GHL contact/opportunity write via API), implemented in `TFRS-Admin/cathy-kitchen-2`#20.
**Why:** D-002 assumed a native form for every customer-facing data path; that's no longer true for weekly ordering, and the gap would otherwise leave the architecture docs describing a flow that doesn't exist. Routing weekly ordering through a GHL-owned number, rather than inventing a Base44-side capture mechanism for it, uses GHL's native SMS/CRM capability instead of duplicating it.
**Implication:** `04-ARCHITECTURE.md`'s weekly-ordering flow, integration data list, and secret names are updated to match (no `GHL_WEEKLY_ORDERS_*` secrets — there is no weekly-order pipeline or function). Any future agent must not reintroduce a native weekly-order form without a new decision superseding this one. The GHL number swap is only a `SiteSettings.sms_number`/`phone_display` data edit, no code change — but that edit happens only once the new number is actually provisioned and confirmed working (D-006 still gates any Base44 secret).

**Why:** Explicit, current owner instruction, per the authority order in `00-README.md` (owner's current instruction ranks above prior documented decisions, including D-002/D-006/D-007/D-008's GHL content).
**Implication:** Catering keeps emailing the owner directly; that part of this decision still holds. Weekly ordering's "GHL dropped, no reintroduction without a new decision" clause is superseded — see D-010. ### D-010 — GoHighLevel reintroduced for weekly ordering only, as a deliberately separate branch; catering stays on plain email
**Status:** Active
**Decision:** The owner reversed D-009's "GHL dropped entirely, no reintroduction without a new decision" for weekly ordering specifically (D-009's catering content is untouched — catering keeps emailing the owner directly). `TFRS-Admin/cathy-kitchen-2` now carries two parallel, both-current implementations of weekly ordering, intentionally not merged into each other:
- **`main`** — unchanged in shape: "Order for N" → an in-page extras picker, if the week has any → a pre-filled `sms:` link to Cathy's own personal number. Now also carries a same-day ordering cutoff shared by both branches: 10:00 AM America/Chicago, kept in one constant (`base44/shared/orderCutoff.js`). A day already past, or today once the cutoff has passed, shows a disabled Order button with a short note instead of a live link.
- **`feature/ghl-order-funnel`** (branched from an up-to-date `main`, so it carries the cutoff too) — "Order for N" → the same extras picker → a native Name + Phone form (required) → a new server-side function, `submitOrder`, which re-validates everything (name, phone normalized to E.164, the same cutoff, a honeypot) and, if it passes, upserts the customer as a GHL contact (tagged `web-order`), adds one new timestamped note with the order, and notifies the owner two ways — a GHL internal comment on her own contact record, and the existing owner-notification email — then shows a confirmation screen. One function builds the order-summary line once per order and that exact string is reused for the note, the notification, and the confirmation, so they can't drift apart. If the GHL call fails, the visitor sees an error and the same `sms:` fallback link `main` uses, so no order is ever silently lost. See that repo's `GHL_SETUP.md` for the required secrets, Private Integration scopes, and a manual test checklist.
**Why:** Explicit, current owner instruction ("we're gonna have to use GHL here... Cathy uses nothing but SMS but she wants a web page... the GHL function is just receiving the order from the site"), per the authority order in `00-README.md`. The owner asked for both branches to be kept current side by side rather than merging one into the other — this is a deliberate parallel comparison of the two integration shapes, not a staged rollout toward a single destination. The system-boundary reasoning from D-002 ("GHL is the sole system of record for customer/order data, never a Base44 entity") still applies to the GHL branch: it writes no customer/order data into Base44.
**Implication:** Neither branch is merged into the other without a further, explicit owner instruction. A non-order-flow fix always lands on `main` first and is then merged into `feature/ghl-order-funnel`, never the reverse. As of this writing, no Cathy's Kitchen GHL location or Private Integration token exists yet — creating both is human-only (no API for either); the GHL branch's code is complete but inert until `GHL_PRIVATE_INTEGRATION_TOKEN`, `GHL_LOCATION_ID`, and `GHL_OWNER_CONTACT_ID` are set as Base44 secrets on that branch. `04-ARCHITECTURE.md`'s weekly-ordering flow, platform-boundary notes, integrations section, and constraints are updated to describe both branches in parallel rather than asserting one as "the" architecture.

### D-011 — Gallery is a standalone photo gallery with admin upload and titles; the dish-card gallery was removed
**Status:** Active; the Implication's seed-script paragraph is superseded by D-012 — no Facebook-photo backfill happens at all now
**Decision:** `TFRS-Admin/cathy-kitchen-2`'s `/gallery` page is no longer derived from `MenuDay` history (one card per distinct dish, with filters by protein/cuisine/diet/ingredient). It is now a plain photo gallery: a new `GalleryPhoto` entity (`photo_url`, `thumbnail_url`, `title` (required), `sort_order`, `is_published`, same public-read/admin-write RLS as `Dish`/`Extra`/`FAQItem`) that Cathy populates herself from a new "Photo Gallery" section on `/admin`, uploading straight from her phone and titling each photo — reusing the existing client-side resize/upload path (`src/lib/uploadImage.js`), extended with a second ~480px thumbnail variant. The public page is a lazy-loaded, fixed-aspect-ratio grid of published photos opening into an accessible lightbox (focus trap, Escape, arrow-key/button prev-next, the photo's title as both caption and alt text); an unpublished photo and a dish/menu item are each independent concepts now — nothing in the gallery is derived from or linked to either. `src/lib/mealGallery.js`, `MealGalleryCard.jsx`, `useMealGallery.js`, and the meal-gallery-specific filtering functions in `src/lib/galleryFilters.js` (the shared protein/diet-tag taxonomy constants there stay, still used by `DishManager.jsx`) were deleted along with the filter sidebar/pagination UI and CSS. A short-lived historical-photo-backfill feature (matching ~85 of Cathy's old Facebook photos to dish names via a static `src/lib/dishPhotos.js` manifest, shown as a small thumbnail on the weekly `DishCard` board and as a `MealGalleryCard` fallback) was merged immediately before this decision and is fully reverted by it — none of that manifest, its generated `public/images/dish-photos/` assets, or the `DishCard`/weekly-board thumbnail wiring survive; the weekly board is text-only again, exactly as before that feature.
**Why:** Explicit, current owner instruction: photos should be a Cathy-curated gallery with her own captions, not an automated derivation of menu history, and not require a photo per dish to look complete. The prior historical-photo-backfill feature's premise (static, dish-name-keyed photos with no human-authored title) was superseded by this same instruction before it saw real use.
**Implication:** `MenuDay.photo_url` and `Dish.photo_url` are untouched and keep their existing meaning (a specific day's or the dish-library's own photo, shown on that day's `DishCard`/in the admin Dish Library) — the gallery reads neither and nothing writes to them from the gallery's upload path. No per-dish photo upload exists outside the Dish Library's own `PhotoPicker` (`DishManager.jsx`); the gallery is the only place Cathy uploads gallery content. A one-time seed script (`TFRS-Admin/cathy-kitchen-2`'s `scripts/gallery-photos/`) matches Cathy's old Facebook photos to a CSV of post dates/captions and creates `GalleryPhoto` records from them (title cleaned from her own caption text, sentence case, no emoji/hashtags/trailing punctuation), keyed for idempotent re-runs by original filename — seeding real data into the account's Base44 app only happens with explicit owner confirmation, never silently.

### D-012 — Gallery seed/Facebook-import plan dropped entirely; Cathy uploads every photo herself, no backfill
**Status:** Active
**Decision:** The Facebook-photo seed script described in D-011's Implication is not used to create any `GalleryPhoto` records, now or later. There is no seeding, no Facebook import, no CSV matching, and no image-hosting work as part of the gallery feature; every photo in the gallery comes from Cathy uploading it herself through the admin Photo Gallery section, from day one including an empty gallery.
**Why:** Explicit, current owner instruction, given after the seed script (`scripts/gallery-photos/` in `TFRS-Admin/cathy-kitchen-2`) and its match/title/publish-flag data were already built and, for the photo files specifically, already merged to `main` (`public/gallery/*.webp`, 84 photos) — but before any `GalleryPhoto` record was created from them. The owner's instruction reverses the backfill premise itself, not just its execution: the gallery launching empty is the intended, acceptable state, not a gap to fill.
**Implication:** No `GalleryPhoto` records exist from the seed data as of this decision, and none will be created from it going forward. The seed pipeline's code (`scripts/gallery-photos/`) and the 84 already-merged image files under `public/gallery/` in `TFRS-Admin/cathy-kitchen-2` predate this decision and are not reverted by it automatically — their removal (or continued, inert presence in the repo) is a separate question for the owner to decide, tracked outside this entry. Any future agent finding that `scripts/` directory or those files should treat the backfill itself as dropped regardless of whether the files are still present, and should not run `node seed.mjs`-equivalent steps or create `GalleryPhoto` records from `working/seed-records.json` without a new, explicit owner instruction overriding this one.

### D-013 — Privacy and Terms pages removed from the live site
**Status:** Active
**Decision:** `TFRS-Admin/cathy-kitchen-2`'s `/privacy` and `/terms` pages — both placeholder "Draft — pending final review" text that was never replaced with real content — are removed entirely: the routes, the footer links, the dead `SiteSettings.privacy_url`/`terms_url` fields, and every other reference (`#62`). The URLs now fall through to the site's existing catch-all not-found page, the same as any other unknown URL.
**Why:** Cathy's Kitchen is a low-data local business with text-first ordering — weekly ordering is a plain `sms:` link (D-008/D-010) and the one native form (catering) emails the owner directly (D-009), collecting name/phone and nothing else. There was no real privacy or terms content to publish, and a placeholder "Draft" page live on a published site is worse than no page at all.
**Implication:** Revisit adding a real privacy page when either the newsletter signup or a texting number via GoHighLevel (D-010's `feature/ghl-order-funnel` branch) goes live on `main` — both usually require one. Until then, no privacy or terms page exists on the site, and no agent should re-add one without a new decision superseding this.
